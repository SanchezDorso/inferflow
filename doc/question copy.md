1. 对比 InferFlow、vLLM、SGLang 的区别、优势，以及这个项目的价值

vLLM 和 SGLang 是线上服务，正在生成的请求不能被新请求卡住

inferflow，在Prefill 采用 FIFO 调度，Decode 阶段支持抢占，在显存压力下可以回滚任务。

你的调度取舍是：优先把当前选中的工作尽快算完，而不是保证已有请求每一轮都能继续生成 Token。

这个取舍在离线负载上是赚的。4090D，256 条，输入 100 到 1024，每条生成 1024，温度 0.6，和 vLLM 0.11.0 对齐配置。我大约 5720 token/s，它大约 5080 token/s，快 12%。前缀命中接近 0，快不是因为少算了 KV。我一页 256 个词，vLLM 一页 16 个，这次有 151 次抢占，页大是我吃亏的地方。SGLang 从第一个词往下对前缀，这项我没同机比过。量化、投机解码和在线接口我没做。

1. 项目的算子是 PyTorch 里面的，还是自己完成的算子开发和定制

矩阵乘、RMSNorm、RoPE、SiLU 都是 PyTorch。自己写的是一个 Triton kernel：把这一步新算出的 K、V 按页内槽位写进缓存。分页读没用自己的 PagedAttention kernel，用的是 FlashAttention 的两个接口，prefill 用变长接口，decode 用带 KV cache 的接口

1. 当前项目有什么可以优化的地方，假如有足够资源

先改调度。现在有新提示，正在生成的请求就停住。测到的结果是旧请求 0 个新词、vLLM 16 个。第一步是把长提示切开，和 decode 放进同一步。

第二改 KV。页从 256 降下来，准入把已经命中的页扣掉。共享长前缀再考虑做成按词匹配的前缀树。现在写满 256 才复用，而且 `can_allocate` 不看命中。

第三按目标卡做算子和通信。KV 写入和注意力后端换成这张卡上更快的实现，all-reduce 和下一层重叠。0.6B 在 PCIe 上不该用张量并行，框架应按模型大小和互联自己选数据并行或张量并行。

第四把 GPU 上和 Hugging Face 的对齐从「前 8 个 token」拉长，再补客户要的模型结构。

4. 为什么你会用两张3080TI来完成这个模型的推理。qwen3-0.6B为什么会用到多卡呢？多卡相比用单卡的好处在哪里？并行策略有什么好处？

0.6B 的权重大约 1.2GB，3080 Ti 12GB 或 4090 24GB 单卡都放得下。两卡不是为了把模型装进显存。

我用多卡是把简历里的张量并行做出来并测掉。结果是两卡更慢：4 条短请求，两卡 2.48 秒，单卡 1.66 秒，输出一致。每层两次 all-reduce，卡间是 PCIe，通信比省下的计算贵。

多卡的好处出现在两个地方。模型或 KV 超出单卡，必须把权重或上下文切开，否则跑不起来。请求多、模型又放得进单卡，就每张卡放一份模型分请求，我在 4 卡上从 5680 做到 18995 token/s，3.34 倍。并行策略是按「放不放得下」和「要吞吐还是要单条延迟」选，不是卡多就切张量。

5. 对于qwen3-0.6B这个模型，什么样的并行方式是最优的？

一张卡就用单卡。多张卡、目标是这批请求的吞吐，用数据并行：每张卡一份完整模型，按已分配的提示长度把新请求交给最闲的卡。不要用张量并行，我测过两卡更慢。它不是 MoE，用不上专家并行。上下文默认 4096，用不上把一条长序列切开的上下文并行。流水线并行的气泡在这么浅的模型上不划算。

6. 怎么避免流水线并行的气泡， bubble 是只有在 decode 才出现吗？

气泡两边都有。流水线把层切到不同卡上，一批数据要先灌满流水线，结束时再排空。这段时间后面的卡是空的。

Decode 更明显。一条请求每次只算一个新词，如果不同时塞进足够多的微批，填充和排空占掉大部分时间。Prefill 的一条长提示本身算得久，气泡比例小一些；只有一个微批时，开头和结尾一样有空泡。

避开的办法是微批够多，用 1F1B 这样的调度让前向和反向，或者推理里的连续请求，把流水线填满。层数少、卡数多的时候，气泡比例下不来，这就是 0.6B 不用流水线的原因。InferFlow 没有做流水线并行。

7. 在prefill 这个阶段，有什么更合适的并行方式吗？分类讨论

Prefill 算整段提示，比 decode 更吃算力，但也更吃卡间通信。

请求多、每条不长、模型放得进单卡：数据并行最好，各卡各算各的提示，没有 all-reduce。这是 0.6B 的情况。我把同一段 prefill 切到 2 卡、4 卡，吞吐从大约 10.6 万 token/s 掉到 5.0 万、4.7 万。

单条特别长、卡间是 NVLink、隐藏维度大：张量并行能把大矩阵拆开，通信的是激活，算力分摊划算。0.6B 隐藏维度只有 1024，PCIe 上不划算。

单条长到几十 K、激活和 KV 单卡放不下：按序列切开，每张卡只拿一段。要交换别的卡上的 K、V，并用在线 softmax 拼回正确结果。通信次数比张量并行多，换来的是每张卡不用放下整段上下文。

8.  TP 会引入什么代价，量化一下

Qwen3-0.6B 有 28 层。每层的 O 投影和 down 投影各做一次 all-reduce，一次前向大约 56 次，外加词嵌入一次。每次的数据量是「这步的词数 × 1024 × 2 字节」。

Decode 一步 128 条请求，每次 all-reduce 大约 256KB，56 次都卡在启动和同步上。单卡 decode 大约 10171 token/s，2 卡 9321，4 卡 8111。

Prefill 一步大约 1.6 万个词，每次 all-reduce 大约 32MB，56 次大约 1.8GB。单卡 prefill 大约 10.6 万 token/s，2 卡 5.0 万，4 卡 4.7 万。省下的矩阵计算盖不住 PCIe 上的通信。

9.  对比 TP 和 CP 。例如上下文有64K，切成8K

张量并行切的是隐藏维度。64K 个词每张卡都看得到，每张卡只算一部分通道，每层用 all-reduce 把部分和拼回来。单卡仍然要放得下 64K 的激活和全部 KV。

上下文并行切的是序列。8 张卡各拿 8K，每张卡只存自己这一段的激活和 KV。注意力要看前面的词，所以必须把别的卡上的 K、V 拿过来，并且按因果顺序拼。RoPE 的位置要用全局位置，不能从 0 再编。

64K 这种长度，我更在意每张卡的激活和 KV 放不放得下，上下文并行对得上这个约束。张量并行对得上「矩阵太大、序列没有长到要切开」。0.6B 默认上下文是 4096，两种都不是我现在的选择。代码里没有上下文并行。

10. CP为了保证切分上下文，最终能推出一个正确的一个结果，相比于不切分来说，它会引入哪些额外的操作来保证这个推理结果是正确的。TP 的时候，每一层需要多两个 allreduce 。CP 的过程中需要引入什么？对比cp和tp引入的代价

只看 Prefill。不切分时，一张卡拿着全部 Q、K、V 做一次因果注意力。

切成 8 段之后，每张卡先只算自己这 8K 的 Q、K、V，位置编码用全局下标。因果注意力规定：后面的段能看见前面的段，前面的段看不见后面的段。所以每张卡要按环把前面各段的 K、V 收过来。不能把每一段的注意力分数矩阵留在显存里，要用在线 softmax：记下当前的最大值和求和，新的一段到来时按最大值的差改缩放，再累加输出。环走完，每张卡只得到自己这 8K 的正确输出。后面的 MLP 是逐词的，拿到完整隐藏向量就可以在本地算。

张量并行每层是 2 次 all-reduce，数据量按「全部词数 × 隐藏维度」算。上下文并行每层是大约 7 次 K、V 传递，数据量按「这一段的词数 × KV 通道」算，而且要串行 7 步才能拼完 softmax。0.6B 上每个词的 K 加 V 大约 4KB，激活大约 2KB，上下文并行搬的字节更多，跳数也更多。它换来的是每张卡只存 1/8 的序列。64K 放不下时这个代价值得付；4096 放得下时不值得。

11. 在多卡的推理里面，对比多进程和多线程，进程和线程各自的特点是什么

我用多进程。一张卡一个进程，rank 0 调度，其余进程等在共享内存上，层内通信用 NCCL。进程之间地址空间分开，一张卡上的上下文不会踩到另一张卡。崩溃时也不会把所有卡一起带走。代价是启动慢，控制信息要序列化进共享内存。

线程共享一块地址空间，交接一个 batch 不用拷贝，适合在同一个进程里让 CPU 组下一批、GPU 算上一批。Python 有全局锁，纯 Python 的调度不会因为开很多线程就变快。一个线程把 CUDA 上下文搞坏，整个进程退出。

所以卡和卡之间我用进程。一个进程内部如果要重叠调度和计算，再用线程。SGLang 就是这个拆法。InferFlow 的调度和前向在同一个进程里串行做完，这部分没有用线程重叠。

12. kv 的缓缓存块的管理，是特指的paged attention吗？

不是同一个东西。块管理是 CPU 上的账本：这一页分给谁、引用计数是多少、哈希对不对、空闲页从哪头取。PagedAttention 是 GPU 上怎么按这个账本读写 KV。

InferFlow 的账本在 `BlockManager`。真正按页读注意力的是 FlashAttention 的分页接口，按页写 KV 的是那个 Triton kernel。没有这个账本，注意力 kernel 不知道历史 KV 在哪一页。

13. 基于哈希匹配的 KV 缓存复用机制，局部命中的时候，怎么处理？比如说我现在来了一个新的序列，这个序序列可能是1024个 token 然后其中其实512个 token 是命中的。也就是说，你会对每一个部分长度都会去做这种哈希的那个计算和匹配吗？

不会对任意长度做哈希。一页 256 个词，只对写满的页做，而且必须从第一页按顺序来。

1024 个词是 4 页。前 512 个词命中，就是前两页的哈希都对上了，而且词本身再对一次，防止哈希撞了。这两页直接共用，引用计数加一，`num_cached_tokens` 变成 512。第三页开始内容不同，链式哈希断了，后面各页全部重算。最后一页即使和别人一样也重算，保证这次 Prefill 至少有一个词能产出下一个词。

所以 1024 里命中 512，算的是前 768 个词里新的那 256，加上最后一页。不会在页的中间，比如第 100 个词，单独做一次匹配。

14. kv 的缓存块的管理。和vllm、sglang的联系和区别

和 vLLM 是同一类账本：逻辑页映射到物理页，写满的页做哈希，引用计数允许多条请求共用，释放后引用归零才回收。差别是我一页 256，vLLM 通常一页 16；我判断能不能进来时不扣除已经命中的页。

SGLang 不用「写满一页才对得上」。它把前缀做成一棵树，从第一个词往下走，走到哪算到哪。调度还可以优先选树上已经有的请求。我的调度只看先来后到，不看谁的前缀更长。

15. pagedattention 的这个 kernel 是自己写的吗？还是用的哪个开，哪哪个公开的版本吗？

读不是我写的。用的是 FlashAttention 2.8.3：prefill 是 `flash_attn_varlen_func`，decode 是 `flash_attn_with_kvcache`，页表传进去。自己写的是写入那边的 Triton kernel，按 slot 把 K、V 写进对应页，slot 为 -1 的位置跳过，这样 CUDA Graph 的填充位不会写坏缓存。

16. 对比FlashAttention3和 PyTorch 的算子来拼凑哪个更快

我现在跑的是 FlashAttention 2，不是 3。3 是给 Hopper 做的，4090 用不上。

和 PyTorch 把 Q、K、V 拼成一次 SDPA 比，FlashAttention 在序列长的时候更快。它按块算注意力，不把整张分数矩阵写回显存。我的 CPU 参考实现就是 SDPA，只用来和 Hugging Face 对结果，速度差一个数量级以上。0.6B、序列只有几百的时候，注意力在总时间里占比不大，快出来的主要是调度开销，不是注意力 kernel。序列到 4096 以上，FlashAttention 和手写 SDPA 的差距才会拉开。

17. 为什么会提倡 PD 分离这样一个部署方式

Prefill 吃算力，Decode 吃显存带宽。放在同一张卡上，一条长提示会把正在生成的请求堵住。我自己的调度就是这样：有新提示，旧请求这一步一个新词都没有。

分开之后，一批卡专门算提示，一批卡专门往外生成，KV 算完传过去。提示的吞吐和每个新词的间隔可以按不同的卡数去配。代价是传 KV 的延迟。0.6B、单机、提示不长的时候，传输可能比堵住那一下还贵，所以我没做。提示长、同时生成的请求多、两边的延迟指标分开考核时，才值得拆。

18. 除了qwen3，对其他的那些模型学习。qwen3已经发布有一段时间了

调度、页管理和多进程执行不绑在 Qwen3 上。绑在 Qwen3 上的是 `models/qwen3.py`：GQA、Q 和 K 的 RMSNorm、RoPE、SwiGLU，以及权重名字怎么切到各张卡。

换一个结构接近的模型，主要改这一层和加载时的名字映射，调度和 KV 可以留下。如果是 MoE、多模态，或者注意力本身变了，要补层，也要补张量并行怎么切。我没有做成任意 Hugging Face 模型直接加载。更新的模型我按这个边界学：引擎复用，结构不同的部分单独写，并用同一套和 Hugging Face 对贪心输出的测试看它有没有接上。

19. 端到端的推理有没有遇到过输出乱码，精度对不齐的情况

遇到过对不齐，不是从第一个词就乱码。CPU 上用一个随机初始化的小 Qwen3，贪心解码和 Hugging Face 逐词一致，说明调度、分页和前缀这条链路的语义是对的。

GPU 上用真实的 Qwen3-0.6B、BF16，只比较前 8 个生成词。再往后两边会分叉。原因是内核不同，BF16 的舍入积累不一样，不是词表切错，也不是权重没加载上。权重没加载上的话，第一个词就会乱。我的加载如果名字对不上会静默留下未初始化参数，所以对 Hugging Face 的前几个词是必要的检查。

20. 提问，你对我们的团队和我们公司这边有没有什么问题？我这边也可以给你做一些问题的解答。

有三个问题，都和我做过的测量有关。

客户的卡之间是 NVLink 还是 PCIe？我在 PCIe 上把 0.6B 做张量并行，两卡比单卡慢。如果你们的卡也是 PCIe，交付时默认不该开张量并行。

客户最后看的是首字延迟、词和词之间的间隔，还是整批吞吐？这三个指标的调度是冲突的。我现在的实现把整批吞吐放在前面，正在生成的请求会被新提示堵住。

注意力和 KV 写入，你们希望落到自家的 Triton 或 TileLang 上，还是可以先用 FlashAttention 这种外部实现把性能跑出来？我现在读用的是 FlashAttention 2，自己只写了写入的 Triton kernel。

21. 部门介绍：我们这个团队是这样的，就是我们相当于是在客户交互的的最后一个环节。也就是说我们上层可以拿到一些基础的软件站，比如说编译器、 Runtime 以及算子库，以及这个PyTorch 这些框架之类的基础设施。那我们这一层的话会基于这些东西去交付一个用于与推理的，一个解决方案，比如说基于 VLM 或者基于 SG 浪。那我们交付到客户手里，就希望说客户拿到我们的卡，以及我们的给出的软件解决方案之后，能够在大模型推理上跑出一个最佳的一个性能。那我们就是去连接底层软件栈和一个好的推理。性能的，这样的一个角色。但是我们不见得所有东西都是特别成熟的，就是我们很多像通用算子库这些当然是可以直接使用。但是我们比如说要做一些融合算子，一些定制算子，一些 Triton 或者是一些 Tailand 的这种算子。甚至到那个可能通信的调优、框架的调优、调度的调这些都是我们这个环节来做。

听到的是：上面有编译器、Runtime、算子库和 PyTorch，你们用这些东西给客户交出能在你们卡上跑出性能的推理方案，缺的算子、通信和调度由你们补。

这和我现在的缺口是对得上的。我的调度能改，但新提示会堵住正在生成的请求。我的注意力读依赖 FlashAttention 2，写入只有一个 Triton kernel，换一张卡就要重做。通信上我测到 PCIe 上张量并行变慢，还没有按互联自动选择并行方式。如果入职，我会先从「这张卡上 all-reduce 和注意力怎么配调度」做起，而不是先重写一个完整的服务框架。
