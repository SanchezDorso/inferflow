# 512 路 × 4096 上下文：InferFlow 超过 vLLM

Qwen3-0.6B，RTX 4090 D。512 条请求，每条 prompt 3968 token，再生成 128 token，序列长度正好到 4096。temperature=0，ignore_eos，块大小 16，显存占用 0.9，前缀缓存关闭，bfloat16 计算。吞吐不含引擎启动。请求是同一组随机 token（种子 0）。输出都是 65536 token，输入 2,031,616 token，合计 2,097,152 token。

优化前 InferFlow 慢大约 18%。最终这一档工作负载是 **49.28 s**，vLLM 0.15.0 在同一预算下是 **61.18 s**。

## 对照

| | 整批时间 | 总 token/s | 输出 token/s | KV |
| --- | ---: | ---: | ---: | ---: |
| InferFlow 优化前，预算 16384，bf16 KV | 70.48 s | 29755 | 930 | 178848 token |
| InferFlow 只把预算提到 65536，bf16 KV | 63.41 s | 33074 | 1033 | 164992 token |
| vLLM 0.15.0，预算 16384，bf16 KV | 60.84 s | 34468 | 1077 | 161152 token |
| vLLM 0.15.0，预算 65536，bf16 KV | 61.18 s | 34280 | 1071 | 同卡同占用 |
| InferFlow 优化后 | **49.28 s** | **42554** | **1330** | 333120 token，fp8 |

优化前的 70.48 s 是本机在现有融合 kernel 上、按原来的 16384 预算重测的。更早一次同等条件记录是 71.59 s，见 `512并发4096上下文.md`。vLLM 把预算从 16384 提到 65536 几乎不变（60.84 s → 61.18 s）。InferFlow 只改预算能到 63.41 s，还是慢大约 2 秒。

优化后相对 vLLM（65536，bf16 KV）总吞吐是 42554 / 34280 = **1.24×**，整批少 11.9 s。

FlashInfer 的 bf16 decode 在这条整批上只从 63.4 s 降到 62.9–63.1 s。decode 已经吃满 KV 带宽，换一个差不多的 kernel 不够越过 vLLM。

## 改了什么

1. **Prefill 预算默认 65536。** 3968 长度一步能放进约 16 条，GEMM 比 16384（约 4 条）更吃满。激活峰值变高，bf16 下 KV 从 178848 token 降到约 16.5 万，但 prefill 步数从大约 128 步降到 32 步。这是 70.48 s → 63.41 s 的主要原因，单独不够赢。

2. **Decode 用 FlashInfer，并且录进 CUDA Graph。** `plan()` 有一次 CPU 同步，留在图外；图里 28 层只重放 `run()`。长度从捕获时的 1 变到 4096，固定 buffer 会在重放前被 `plan()` 更新。batch 16、上下文约 4000 时，eager 的 FlashInfer 一步要 27 ms（kernel 只有约 10 ms，剩下是 launch 空隙）；收进图之后是 11.5 ms。batch 32 对齐时，FA3 图重放约 24 ms，FlashInfer 约 20 ms。短提示上 8 个贪心 token 与 FA3 一致。

3. **CUDA Graph 在 16–128 之间按 8 对齐。** 原先 16 一档，常驻大约 40 条会被抬到 48，多读一截 KV。bf16 整批上这一项没有单独拉开差距（62.92 s → 63.06 s，落在噪声里）。fp8 之后常驻 batch 更大，这档对齐仍然留着。

4. **前缀缓存关闭时，KV 用 fp8 e4m3。** 这是越过 vLLM 的一步。同样 17.79 GiB 的 KV，token 容量从 10410×16 变成 20820×16（333120 token，大约 81 条满 4096）。decode 每个 token 的 KV 字节减半。单层、batch 40、上下文 4096：bf16 0.724 ms，fp8 0.384 ms（1.88×），注意力输出最大误差 0.0068。写入页的最大误差 0.125，是 e4m3 的量化台阶。

   前缀缓存打开时仍然用 bf16。FA3 的分页 prefill 要求 Q 和 K 同 dtype，fp8 页在混批或前缀命中时改走 FlashInfer 的 paged prefill。纯 prefill（没有页表）仍用 FA3，K/V 在进页之前是 bf16。

   环境变量 `INFERFLOW_FP8_KV=0` 或 `INFERFLOW_FLASHINFER=0` 可以退回。

## 数值

fp8 KV 会改变贪心结果。两条短提示、各生成 8 token：第一条与 bf16 相同，第二条从第 1 个生成 token 就分叉。这次对比衡量的是墙钟，不是逐 token 一致。

vLLM 0.15.0 在同样的 65536 预算、占用 0.9、块大小 16 下打开 `kv_cache_dtype=fp8`，引擎初始化之后第一次 generate 报了 CUDA out of memory，没有跑出可对照的 fp8 数字。上面的 vLLM 列都是 bf16 KV，并且都完整返回了 65536 个输出 token。

## 怎么测的

InferFlow 优化后：`max_model_len=4096`，`max_num_seqs=512`，`max_num_batched_tokens=65536`，`gpu_memory_utilization=0.9`，`enable_prefix_caching=False`。启动 7.35 s（不含在吞吐里）。整批 49.28 s，抢占 12 次。CPU 侧 `tests/test_block_manager.py`、`tests/test_scheduler.py`、`tests/test_engine_cpu.py` 共 21 项通过。
